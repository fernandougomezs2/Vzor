# v0.4.2-B Python/Rust materialization audit

## Scope and invariant

This subphase reduces transient materialization at the private pandas/PyO3
boundary only. It does not add a public API, dependency, backend, Arrow
transport, unsafe code, parallelism, GIL-release path, or timing field. The
package remains `0.3.2`; `output_version = 1` and `format_version = 1` remain
unchanged.

The Rust core still owns one `Vec<ProfileValue>` per input column. That owned
representation is required by the existing profiling, schema, inspection, and
validation paths and was not changed.

## Before the change

`_normalize_dataframe` iterated every pandas `Series` into a full Python
`list`. Each value was normalized in Python before PyO3 received a
`Vec<Py<PyAny>>`; the binding then iterated that vector to construct Rust's
`Vec<ProfileValue>`. During that conversion, the complete Python list, its
normalized scalar objects, and the Rust-owned vector could coexist.

The audit also identified pre-existing, intentional work outside this change:

- object dtype inference creates a null mask and filtered `Series`;
- datetime values are transported as one ISO-8601 string per row;
- categorical values are expanded per row;
- the Rust core retains result-owned values where its cardinality policy calls
  for them, and exact string unique counting owns string entries.

## Change

The adapter now returns either a private normalizing generator or the original
`Series` plus a private `raw_scalars` marker. PyO3 consumes that iterable
directly while building the existing Rust-owned vector; there is no longer a
complete normalized Python list or `Vec<Py<PyAny>>` at the boundary.

The direct scalar path is deliberately narrow:

- signed integer series without nulls;
- float series (Rust maps `NaN` to the existing null representation);
- Boolean series without nulls.

Nullable integers and Booleans, unsigned integers, strings, object,
categorical, datetime, and unknown columns retain the normalizing generator.
That preserves the established Python checks, including i64 overflow, nulls,
datetime ISO transport, category validation, and object-dtype errors.

This is not zero-copy: pandas still yields Python scalar objects and Rust still
creates its owned `ProfileValue` vector. It only removes the redundant
whole-column Python materialization between those two stages.

## Regression coverage

The materialization test covers signed `int64`, `uint64` values within i64,
`float32`, nullable `Int64`, nullable Boolean, pandas string, object Unicode,
categorical, naive and timezone-aware datetimes, and all-null columns. Existing
dtype and edge-case tests cover uint overflow, mixed object `TypeError`,
`NaN`, infinities, negative zero, and the public profile/schema/inspection
semantics.

## Final isolated benchmarks

Executed on Windows 10.0.26200, AMD Ryzen 7 7730U (16 logical CPUs), 15.343
GiB RAM, CPython 3.12.10, pandas 3.0.5, Vzor 0.3.2. Each operation ran in an
isolated child process against the fixed one-million-row Parquet fixture. Read
time is the median Parquet load time; Vzor time excludes that load. Peak is the
maximum process working set across repetitions.

| Workload | Repeats | Read s | Vzor s (median) | rows/s (median) | Peak working set |
| --- | ---: | ---: | ---: | ---: | ---: |
| numeric profile | 2 | 0.169 | 5.057 | 198,797 | 780,808,192 B (744.6 MiB) |
| baseline profile | 3 | 0.207 | 25.494 | 39,225 | 1,768,394,752 B (1,686.5 MiB) |
| baseline inspect | 2 | 0.198 | 28.149 | 35,529 | 1,767,436,288 B (1,685.6 MiB) |
| many_nulls profile | 2 | 0.178 | 17.848 | 56,599 | 1,049,718,784 B (1,001.1 MiB) |
| heavy_strings profile | 1 | 0.501 | 17.797 | 56,191 | 4,381,687,808 B (4,178.7 MiB) |
| categorical profile | 2 | 0.081 | 3.310 | 302,814 | 504,709,120 B (481.3 MiB) |

Relative to the v0.4.2-A measurements on the same machine, baseline profile
improves from 27.791 s / 2,959,568,896 B to 25.494 s / 1,768,394,752 B
(-8.3% time, -40.2% peak). Baseline inspect moves from 27.854 s /
2,958,192,640 B to 28.149 s / 1,767,436,288 B (+1.1% time, -40.3% peak).
Heavy strings improves from the 0.4.2-A 20.730 s / 6,253,297,664 B result to
17.797 s / 4,381,687,808 B (-14.1% time, -29.9% peak).

Compared with the v0.4.1 reference, numeric improves from 8.263 s / 1,304 MB
to 5.057 s / 781 MB, while many-null input reduces peak memory from 1,582 MB
to 1,050 MB but takes 17.848 s versus 14.191 s. The categorical v0.4.1
reference had highly variable individual repetitions, so its independently
reported medians are not suitable for a strong speed claim.

## Measured and suspected bottlenecks

Measured: the removed list/vector boundary materially lowered peak working set
in the baseline and string-heavy workloads. `many_nulls` remains slower than
its v0.4.1 reference despite its lower peak, showing that per-value null
normalization is still significant.

Suspected, not optimized here: Python scalar iteration and `pd.isna` on the
generator path; object masking; datetime `isoformat`; category expansion; and
Rust string ownership/unique-count hashing. They are candidates for a later
explicit subphase, not changes made by v0.4.2-B.
