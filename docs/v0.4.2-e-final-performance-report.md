# v0.4.2-E final performance report

## Scope and conclusion

This is the final hardening and benchmark record for v0.4.2. It makes no runtime code change: there is no API, semantic, package-version, dependency, CLI, persistence, HTML, or agent-output change. `vzor.__version__` and `vzor.version()` are both `0.3.2`; `output_version = 1` and `format_version = 1` remain unchanged.

The final measurements are local, process-isolated pandas runs. `read` is the median Parquet input-load time; `Vzor` is the median operation time excluding that read; `peak` is the largest process `peak_working_set_bytes` across repetitions. Rows/sec is the median operation throughput. The JSON source records are retained outside the repository in `C:\VzorBenchmarks` as `after_042e_final_*.json`.

## Environment

- HP Laptop 15-fc0xxx; AMD Ryzen 7 7730U with Radeon Graphics (8 cores, 16 logical CPUs); 15.343 GiB physical RAM.
- Windows 11 (`10.0.26200`), AMD64; CPython 3.12.10 in the project `.venv`.
- pandas 3.0.5; Vzor 0.3.2; local Parquet inputs; no network access.
- Each operation used a new process. 100k used three repetitions and 1M used two repetitions. The benchmark runner reports process peak working set, not a Rust-only allocation measurement.

## 5M safety decision

There was no 5M baseline fixture in `C:\VzorBenchmarks\datasets`. Scaling the final 1M baseline profile peak linearly gives approximately 8,557 MiB (8.36 GiB), before uncertainty from constructing a new 5M pandas fixture or concurrent desktop/system use. On this 15.343 GiB machine, Windows memory-counter queries failed, so available physical memory and paging pressure could not be established reliably. The fixture was therefore not generated and no 5M operation was run. This is a safety stop, not a claim of 5M support or a benchmark result.

## Measured bottlenecks and follow-up boundaries

The three largest operation times in the final 1M baseline matrix are compare (56.979 s), schema drift (48.520 s), and profile (27.414 s); inspect (26.636 s) and validate (25.177 s) follow closely. The largest measured peaks are heavy strings profile (3,597.3 MiB), baseline compare (2,733.8 MiB), and baseline schema drift (2,647.5 MiB).

Measured facts: comparison still has to produce its contractually owned snapshots; large string datasets still dominate process working set; and the runner includes pandas dataframe construction/loading plus Python/Rust bridge cost in its process metric. Suspected, not newly optimized, contributors are Python object-string representation, exact hashing/cardinality work, and the remaining dataframe-to-core conversion. They require a separately scoped future phase and allocation-focused instrumentation before changing code.

No dependency was added in v0.4.2-E; optional pandas reader engines remain user-installed, not runtime requirements.

- `cargo fmt --check` passed; `cargo check --locked` passed; `cargo test --locked` passed (133 tests); and `pytest -q` passed (300 tests).
