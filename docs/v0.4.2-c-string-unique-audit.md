# v0.4.2-C string and exact unique-count audit

## Scope and contracts

This subphase optimizes only the internal string path used by exact profiling.
The package remains `0.3.2`; `output_version = 1` and `format_version = 1`
are unchanged. Exact `unique_count`, first-seen observed-value order,
`MAX_OBSERVED_VALUES = 50`, null semantics, public API, report models, CLI,
HTML, persistence, comparison, and drift are unchanged. No dependency, Arrow,
Polars, hasher replacement, preallocation by row count, thread, GIL, or unsafe
code was added.

## Initial ownership audit

| Location | Classification | Finding |
| --- | --- | --- |
| PyO3 `profile_value_from_bound` | Necessary input ownership | Extracting a Python string creates `ProfileValue::String(String)` owned by `DatasetInput`. The current Rust input needs that ownership for later profiling/schema work. |
| `profiling::count_unique` | Redundant clone removed | `UniqueValue::String(value.clone())` duplicated every distinct string into `HashSet<String>`. |
| Exact unique set | HashSet ownership avoided | The set can safely retain `&str` for the scoped profile pass because `DatasetInput` outlives it. |
| `schema::collect_strings` | Necessary result ownership | Its `HashSet<&str>` is already borrowed. The clone into `ObservedValue::String` is necessary for the output model, and is bounded to at most 50 distinct values. |
| Object dtype inference | Deferred | pandas still builds the null mask and filtered Series needed to validate homogeneous string object columns. |

## Structure before and after

Before, `count_unique` transformed every input string into a cloned
`UniqueValue::String(String)` before insertion into the standard `HashSet`.
After, `UniqueValue<'a>::String(&'a str)` borrows the string slice held by the
already-owned `ProfileValue`. Integers, floats, and Booleans retain their prior
copied scalar representations. The `HashSet` remains the standard exact Rust
set and traverses every non-null value.

This eliminates one owned string allocation and payload copy for each distinct
input string in exact unique counting. It is not zero-copy end to end: Python
to Rust extraction and final observed-schema output ownership remain necessary.

## Observed values and early stop

The existing `unique_count <= MAX_OBSERVED_VALUES` gate is retained as the
early stop for observed-value collection: high-cardinality string and
categorical columns return `None` before `collect_strings` runs, so Vzor never
clones thousands or millions of values for `observed_values`. Exact
`unique_count` still scans the whole input. For the eligible path,
`collect_strings` now reserves at most the known distinct count (therefore at
most 50) for its borrowed set and owned output vector. It does not reserve by
row count.

## Regression coverage

New public regressions cover duplicate and all-unique strings; 50, 51, and 100
distinct values; empty and null-like strings; nulls; Spanish accents, `ñ`,
emoji, CJK UTF-8, and long Unicode values; first-seen order; and categorical
cardinality/order. Existing tests continue to cover the complete observed-value
policy and mixed object errors.

## Benchmarks

All operations use isolated child processes on Windows 10.0.26200, AMD Ryzen
7 7730U (16 logical CPUs), 15.343 GiB RAM, CPython 3.12.10, pandas 3.0.5, and
Vzor 0.3.2. Times exclude Parquet load; peak is maximum working set.

| Workload | Before (s / rows/s / peak) | After (s / rows/s / peak) | Change |
| --- | --- | --- | --- |
| 1M heavy_strings profile, 1 run | 17.797 / 56,191 / 4,381,687,808 B | 17.526 / 57,057 / 3,761,258,496 B | -1.5% s, +1.5% rows/s, -14.2% peak |
| 1M high_cardinality profile, 2 runs | 15.529 / 66,335 / 1,625,956,352 B | 15.668 / 63,940 / 1,013,043,200 B | +0.9% s, -3.6% rows/s, -37.7% peak |
| 1M baseline profile, 3 runs | 25.494 / 39,225 / 1,768,394,752 B | 20.058 / 49,854 / 1,789,169,664 B | -21.3% s, +27.1% rows/s, +1.2% peak |
| 1M baseline inspect, 2 runs | 28.149 / 35,529 / 1,767,436,288 B | 19.958 / 50,134 / 1,771,933,696 B | -29.1% s, +41.1% rows/s, +0.3% peak |
| 1M categorical profile, 2 runs | 3.310 / 302,814 / 504,709,120 B | 1.974 / 506,903 / 503,054,336 B | -40.4% s, +67.4% rows/s, -0.3% peak |

The heavy, baseline, inspect, and categorical before values are v0.4.2-B
release measurements. The available high-cardinality reference predates B, so
its comparison is useful for the memory inventory but does not isolate C from
all earlier work. Windows timing varied between isolated repetitions; the
string-specific result supported by both references is the substantial peak
reduction in high-cardinality and heavy-string input.

The required 100k almost-unique high-cardinality stress fixture was generated
deterministically with the existing benchmark generator: 2 repetitions, 0.060
s median Parquet load, 1.152 s Vzor time, 88,335 rows/s, and 208,924,672 B
(199.2 MiB) peak. The existing heavy-string fixture contains 16-, 64-, and
256-character ASCII/Unicode columns; the runner measures that mixed fixture
as a whole, so no new width-specific datasets were added.

## Allocation and remaining debt

No allocation profiler already available to the repository could provide a
trustworthy allocation count, and no runtime instrumentation was added. The
measured working-set reductions are the allocation evidence retained here.

Remaining work is intentionally deferred: Python object/string normalization
and `isna` masking, PyO3 string extraction, datetime string transport, result
ownership for observed values, and comparison/drift paths. v0.4.2-D may audit
comparison and drift after explicit authorization; it is not started here.
