# Vzor v0.4.6 — Compatibility, CI & Wheels

## Scope

This subphase formalizes compatibility and distribution verification. It does
not change Rust profiling, Python normalization, report models, public API,
CLI semantics, persistence, HTML output, package version, or dependency major
versions. The private backend dispatcher restores the established `TypeError`
for unsupported inputs in a base-only install, instead of leaking a missing
optional-dependency error. No package is published, tagged, released, or pushed
by these workflows.

## Candidate support policy pending remote CI

| Surface | Supported range | Evidence lane |
| --- | --- | --- |
| Python | CPython `>=3.12,<3.14` (3.12 and 3.13) | Core CI matrix |
| Platforms | Windows x86-64 and Linux x86-64 | Core CI and wheel matrix |
| pandas | `>=2.2.3,<4` | Minimum/current pandas lanes |
| Polars extra | `>=1.0,<2` | Minimum/current optional-Polars lanes |

The lower pandas bound is 2.2.3 because it is the first pandas 2.2 release
documented as generally compatible with Python 3.13. Polars is optional:
installing the base wheel does not install or require it. The adapters use
documented public pandas and Polars interfaces only; no backend private API is
part of this compatibility contract.

Python 3.14 is ecosystem context, not a Vzor support claim. It has no local or
CI evidence in this subphase. ABI3 was evaluated and deferred: the current
PyO3/maturin configuration produces one wheel per CPython ABI, which makes the
tested interpreter boundary explicit. Enabling ABI3 would require a separate
configuration and full 3.12/3.13 validation before reducing artifact count.

The following targets remain outside v0.4.6: macOS, Linux ARM64, Windows ARM64,
32-bit platforms, and musl-based Linux. They must not be described as supported
until they have a matching wheel and successful test evidence.

## Installation examples

From a built wheel, the base installation keeps Polars absent and fully supports
pandas:

```text
python -m pip install dist/vzor-0.3.2-<tag>.whl
```

Install the optional backend through the wheel's declared extra:

```text
python -m pip install "vzor[polars] @ file:///absolute/path/vzor-0.3.2-<tag>.whl"
```

For source development, create a clean supported virtual environment and run
`python -m maturin develop --release --locked`.

## CI and wheel design

`.github/workflows/ci.yml` contains:

- a Windows/Linux × CPython 3.12/3.13 core lane running `maturin develop`,
  Cargo checks/tests, Python tests, API version smoke checks, and `vzor version`;
- Ubuntu pandas lanes for 2.2.3 and the current selected 3.x release on both
  supported Python versions;
- Ubuntu optional-Polars lanes for 1.0.0 and the latest release permitted by
  `<2`, with direct and mixed-backend smoke coverage; and
- a fresh Linux wheel install without Polars.

It also includes a separate fresh Linux wheel install with the `polars` extra.
The path compatibility regression invokes every public CLI command and exports
all four report HTML types through paths containing spaces and Unicode. A
POSIX-only test verifies that HTML export propagates the normal `PermissionError`
from a non-writable directory; it is deliberately run in Linux CI rather than
pretending Windows has identical permission semantics.

`.github/workflows/wheels.yml` builds Windows and manylinux 2014 x86-64 wheels
for CPython 3.12 and 3.13, creates a clean virtual environment for each wheel,
performs a pandas profile smoke test, and uploads `dist/*.whl` as a workflow
artifact. The workflow is pull-request/manual only and has read-only repository
permissions; it has no publishing credentials or release step.

Expected remote artifact families are CPython-specific Windows `win_amd64` and
manylinux x86-64 wheels. Artifact availability and Linux tags must be reported
from the actual GitHub run rather than inferred locally.

## Local Windows evidence

The base interpreter had disappeared from the path recorded in `.venv`:
`py -0p` reported no installed Pythons and `.venv/pyvenv.cfg` named the missing
Python 3.12.10 executable. CPython 3.12.10 x86-64 was repaired in its existing
per-user location, then `.venv` alone was recreated and Vzor was rebuilt with:

```text
python --version                         Python 3.12.10
python -c "import sys; print(sys.executable)"
python -c "import vzor; print(vzor.__version__)"  0.3.2
python -m maturin develop --release --locked
```

A local `vzor-0.3.2-cp312-cp312-win_amd64.whl` (289,685 bytes) was inspected:
it contains the CPython 3.12 Windows extension and package metadata, and does
not contain benchmark data, build targets, virtual environments, or bytecode
cache directories. A fresh virtual environment installed that wheel without
Polars and successfully profiled a pandas DataFrame. Separate local fresh
environments exercised pandas 2.2.3 and Polars 1.0.0, including mixed pandas /
Polars validation, comparison, and schema-drift smoke checks.

`tests/test_compatibility_paths.py` exercises CLI schema persistence,
validation, and standalone HTML export through directory and filenames
containing spaces and Unicode. The current local Windows filesystem evidence is
therefore direct; Linux path and permission behavior belongs to the remote CI
matrix.

## Gate status

Local Windows/CPython 3.12 restoration and wheel smoke coverage are complete.
The repository has not been pushed or dispatched by this subphase, so GitHub
has not yet produced remote Python 3.13/Linux CI results or wheel artifacts.
Remote green CI remains the final compatibility gate; it cannot be claimed
until the workflows run on GitHub.

## Reproducibility record

The local evidence used Windows 11 x86-64, CPython 3.12.10, Rust stable,
maturin 1.15.0, PyO3 0.23.5 from `Cargo.lock`, pandas 2.2.3 (minimum) and
3.0.5 (current selected release), plus Polars 1.0.0 (minimum) and 1.44.2
(current selected release). The local wheel tag was
`cp312-cp312-win_amd64`; remote Linux wheel tags are intentionally left pending
the actual manylinux job instead of guessed from configuration.
