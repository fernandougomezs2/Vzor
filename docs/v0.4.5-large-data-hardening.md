# v0.4.5 large-data hardening

## Methodology and guardrail

Benchmarks use deterministic Parquet fixtures outside the repository, isolated
child processes, and separate Parquet load and Vzor operation timers. They now
record `available_ram_bytes`, working set after loading, peak working set, and
`peak_delta_above_loaded_dataframe_bytes`. The guardrail is benchmark policy,
not runtime behavior: begin a new scale only when a linear extrapolation of the
last isolated peak is at most 70% of total physical RAM and, when available,
70% of currently available physical RAM. Classifications are local evidence:
Comfortable <=50% physical RAM; Acceptable <=70%; Memory pressure <=85%; Unsafe
above that; Not executed when the guardrail blocks it.

Hardware: HP Laptop 15-fc0xxx, AMD Ryzen 7 7730U, 16 logical CPUs, Windows
x86-64, 15.343 GiB RAM, CPython 3.12.10, pandas 3.0.5, Polars 1.44.2 and Vzor
0.3.2. At the 2M decision point, physical available RAM was about 4.97 GiB.

## Fixtures and progressive result

Existing 1M fixtures cover baseline (30 columns), numeric (15), many_nulls
(20), high_cardinality (10), heavy_strings (6) and categorical (4). This phase
generated the deterministic external fixture
`C:\VzorBenchmarks\datasets\vzor_2000000_baseline_30c_seed42.parquet`
(157,996,019 bytes). No 3M or 5M fixture was generated.

The 1M-to-2M Polars profile peak ratio is 1.92 and time ratio is 1.45:
linear-ish peak growth, with faster observed throughput at 2M. Its 3M peak
projection is about 4.09 GiB. The available-memory guardrail allowed only about
3.28 GiB at that point, so 3M and 5M were not started. The pandas 2M projection
was similarly too close to the available-memory limit for safe unattended work.
No swap, crash, OOM, corruption or temporary benchmark artifact was observed.

## Profile coverage and limits

The prior 1M Polars evidence remains: numeric 4.244 s / 623.3 MiB;
many_nulls 6.046 s / 920.1 MiB; high-cardinality 13.508 s / 936.4 MiB;
heavy_strings 6.850 s / 2,465.3 MiB; categorical 1.205 s / 381.5 MiB.
Heavy strings is the highest-risk profile and was not scaled beyond 1M. Numeric,
many_nulls, categorical, high-cardinality and wide 2M/3M runs were not started
because the baseline guardrail had already blocked the next row scale. The wide
generator is deterministically tested at 250 columns, but no large wide fixture
was created. This is intentional safety coverage, not missing success evidence.

Validation, compare and schema drift retain their existing small/1M benchmark
evidence; no 2M compare/drift was started because they require before and after
inputs and are materially more conservative than profile. CLI remains pandas
only. Large cross-backend equivalence is spot-checked through the existing
deterministic parity tests; complete equality stays on small frames to avoid
duplicating large-frame memory.

## Stability and deferred work

Ten 100k pandas profile calls in one process produced equal profiles; working
set changed from 170,172,416 to 164,220,928 bytes (-5,951,488), which shows no
accumulating growth in that check. Process isolation provides the complementary
release check. These observations do not diagnose allocator caching as a leak.

The public API, `__all__`, dependencies, package version 0.3.2,
`output_version = 1`, and `format_version = 1` are unchanged. No Arrow buffer
redesign, null bitmap transport, timestamp transport, distributed mode, 5M
stress test or 20M–50M experiment occurred. Future work requires a fresh
guardrail decision and allocation-focused evidence, not an inference from this
machine.
